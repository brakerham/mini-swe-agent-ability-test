# 评分规则

## 主要指标

一个任务尝试只有同时满足以下条件，才记为 `resolved`：

1. 提交通过路径与完整性检查，且没有修改受保护文件。
2. 原版公开测试全部通过。
3. 独立验收测试中的 `FeatureTests` 全部通过。
4. 独立验收测试中的 `RegressionTests` 全部通过。
5. 测试实际执行完成，没有超时、评分基础设施错误或测试收集失败。
6. 对 `run` 自动运行，agent 在预算内主动提交；模型错误、步数耗尽或运行超时不记为自主完成。手动 `grade` 只判断候选补丁的功能结果。

主要指标：

```text
resolved rate = resolved 的任务尝试数 / 预先计划的任务尝试总数
```

六项任务使用相同重复次数时，该指标等于每项成功率的宏平均。应同时显示分子与分母，例如 `7/18`。这只是公式示例，不是本项目已取得的模型成绩。

## 部分分

部分分帮助定位“完成了一部分需求”的情况，不能替代 resolved rate。

```text
提交不合规，或任一公开/回归测试未通过，或自动运行没有正常提交：partial_score = 0
否则：partial_score = 通过的 FeatureTests 数 / FeatureTests 总数
```

JSON 字段 `partial_score` 的范围为 0 到 1，显示为百分制时乘以 100。本版本清单中六个任务的权重均为 1，每项重复次数相同，`partial_score_mean` 为所有预定尝试的平均分。权重不得根据某个系统的实测表现修改。逐项任务的通过数与尝试数用于定位能力短板。

测试方法是最小计分单位。一个方法内包含的多个断言或参数样例共同决定该方法是否通过，不能将断言数量解释为独立样本数量。验收测试使用固定、可复现的输入，不依赖网络、当前时间或随机运行顺序。

## 状态解释

| 情况 | 是否 resolved | 如何报告 |
| --- | --- | --- |
| 提交合规，全部测试通过 | 是 | 成功并保留逐项测试证据 |
| 功能测试部分通过，公开和回归全部通过 | 否 | 失败，保留部分分和具体失败项 |
| 公开测试或回归测试失败 | 否 | 失败，部分分为 0 |
| 修改受保护文件、符号链接或路径越界 | 否 | 不合规，部分分为 0 |
| 达到 agent 步数或时长限制 | 否 | 自动运行保留独立评分的 `functional_resolved`，但不记自主完成，部分分为 0 |
| 模型接口、容器或评分器异常 | 否 | 单列基础设施/运行错误，不能记成能力成功 |
| 计划的尝试没有运行或结果缺失 | 否 | `not_run`/缺失，保留在预定分母中 |

agent 声称“完成”、最终回复看似正确、公开测试通过，都不足以单独判为成功。测试没有被发现、被跳过、被预期失败标记吞掉，也不能被当作通过。`invalid_submission` 表示提交不合规，`invalid_result` 表示评分没有产生完整可信的测试记录；`agent_error` 表示模型/agent 未正常提交，`infra_error` 表示运行基础设施异常，`missing` 表示计划中的结果文件缺失。

自动运行的 `functional_resolved` 单独记录停止后的补丁是否通过全部测试，便于区分“补丁行为满足要求”与“agent 自主完成”。它不替代主要指标。即使这个字段为真，只要自动运行因预算或错误未提交，主要 `resolved` 仍为假。

## 基准自身的验收

基准发布前必须验证：

- 每个初始任务的公开测试通过。
- 每个初始任务至少有一个功能验收失败，确保存在可测的待完成工作。
- 每个参考修复的公开、功能和回归测试全部通过。
- 评分器能拒绝受保护文件修改和越界提交，并且不会执行候选自带的验收脚本。
- 相同输入的离线评分结果一致；用量和耗时等运行元数据除外。

这些验证属于评测工具质量检查，不属于 mini-swe-agent 或 DeepSeek V4 Pro 的实测结果。

## 成本与工程质量

耗时、步数、请求数、可获得的 token 用量和费用作为辅助指标报告，不给模型能力分数加权。费用缺失应明确显示未知。低成本但未解决任务的尝试不能被算作成功。

本版本以可执行行为测试为自动评分依据，不自动声称补丁具备生产级可维护性。可以另做人工审阅，观察复杂度、可读性、重复逻辑、错误信息和必要测试，但人工意见须与自动 resolved rate 分开，公布标准并在不知道模型身份时审阅。
